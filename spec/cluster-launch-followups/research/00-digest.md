# Research digest — cluster-launch-followups

Three briefs, fanned out because the change touches two high-blast-radius files (`server.py`,
`cluster/remote.py`), plus the plan's own probes (PLAN §4). One recommendation per question.

| Question | Decision | Source |
|----------|----------|--------|
| What does a locked read raise, and is the session usable after it? | `sqlalchemy.exc.OperationalError` wrapping `sqlite3.OperationalError('database is locked')`, `sqlite_errorcode` 5, after the 5 s busy wait. The per-thread `scoped_session` stays usable: the next read on the same thread works with no `rollback()`. A read whose lock is released during its wait succeeds. | [02](02-locked-reads.md) §1 |
| How is "locked" told apart from other errors? | A new narrow predicate `database_locked(error)` in `cluster/watch.py`: an `OperationalError` whose `orig` is a `sqlite3.OperationalError` with `sqlite_errorcode & 0xFF` in {5 BUSY, 6 LOCKED} (extended 262 "database table is locked" masks to 6), falling back to the message (`database is locked` / `database table is locked`) when the code is absent (a hand-made error). `data/upgrade.py::_is_locked` is not reused: it also matches PostgreSQL 55P03 and lives in a file this cycle leaves alone. | [02](02-locked-reads.md) §2 |
| Catch per read or per check? | Per check state: around `count_failures` in `AutoScaler.check` and around `check_zones` in `check_fixed`/`check_dynamic`. Every read in those states comes before any state change, so a skipped check leaves the machine consistent; a non-lock error is re-raised bare (R4). Not in `demand.py`: `hs server --autoscaling`'s `TopologyPublisher` calls it directly and must not change. | [02](02-locked-reads.md) §3, §5 |
| How are exits seen during a skipped check carried (R2)? | `AutoScaler.unchecked`: `check()` reads `exited = unchecked + clean()`, keeps it in `unchecked` until `count_failures` returns, then clears it. `last_check` is set before the reads, so a skipped check is retried one period later. | [02](02-locked-reads.md) §3 |
| R3: where, and how does it "read again"? | In `work_remains`, around both `scheduled_work` calls: on a locked read, one WARNING and `False`. `watch_launched` already calls it again every `WATCH_INTERVAL` (1 s). Worst case after the release ≈ 1 s + barrier + read + 2 s settle + read + stop, well inside 10 s (probe: 12 s run, ended 3 s after release). | [02](02-locked-reads.md) §4; PLAN §4 probe |
| The `--no-db` count | `Receiver.written`, an int incremented by the one receiver thread after each APPLIED result, in both modes (STALE, DUPLICATE, DEFERRED `continue` first). Read by the watch thread after the `results_written` barrier, which makes it exact. Predicate: server ended or no submitter → no work; submitter alive (input still being read) → work; else `written < submitter.task_count`. `<`, not `!=`. No queue, thread, join or wire change; §6 untouched. | [01](01-receiver-count.md) |
| Keep `MEMORY_SETTLE`? | Drop it (and the `memory_settle` parameter and the known-gap docstring paragraph). Its only job was letting a finished server end before "alive" counted as work; the exact count does that. R6 gets ≈ 3 s of margin back (probe: `nodb-fail` 9 s → 4 s). Nothing outside `watch.py` references it. | [01](01-receiver-count.md); PLAN §4 probe |
| Who inherits R1's handling? | Relay site fleets (`SiteScaler` subclasses `AutoScaler`, overrides `check_zones` but not `check`/`check_fixed`/`check_dynamic`; `failed_launches` 0 there). `hs server --autoscaling` does not (no `AutoScaler`). Both acceptable under the GOAL gate. | [02](02-locked-reads.md) §5 |
| Deterministic tests | See [03](03-tests.md): real `BEGIN EXCLUSIVE` from a second connection on the test's own SQLite file, with a short busy wait for in-process unit tests and the default 5 s for subprocess drives; every subprocess and join bounded. | [03](03-tests.md) |
| Can a drive hold the lock without the server's own threads meeting it? | Only when the scheduler is asleep. With a client connected, the scheduler reads on every request and dies on the lock (a Non-goal, not this cycle's). The working-launcher drive therefore holds the lock once every task is done, the clients have left (`-T 1s`) and the scheduler's TRACE log says it is backing off 16 s or more (`-Q 60s`). | PLAN §4 probe |
